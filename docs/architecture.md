# 架构与一致性设计说明

## 1. 分层

```
            ┌──────────────────────────────┐
HTTP 层     │ fleet/api.py (FastAPI 路由)   │  GET / 保持原样
            └───────────────┬──────────────┘
            ┌───────────────▼──────────────┐
服务层      │ fleet/service.py             │  声明校验、幂等提交、查询、取消
            └───────────────┬──────────────┘
            ┌───────────────▼──────────────┐
编排层      │ fleet/engine.py              │  调度扫描、派发、看门狗、
            │                              │  有界重试、容量回收、事件日志
            └───────┬───────────────┬──────┘
            ┌───────▼──────┐ ┌──────▼─────────┐
执行层      │ executor.py  │ │ store.py       │
            │ 执行单元/行为 │ │ 内存状态/账本   │
            └──────────────┘ └────────────────┘
```

- **executor** 不做调度决策，只提供 `can_accept/acquire/release/run`，
  执行结果由 `StepBehavior` 脚本确定（确定性、可复现）。
- **store** 是状态唯一事实来源：一把 `RLock` 保护任务/步骤状态机、
  尝试记录与容量账本相关的判定数据。
- **engine** 拥有线程池与超时看门狗，所有状态流转都在 store 锁临界区内调用；
  执行（可能 sleep/delay）在锁外的线程池中进行，只有"结果收口"时短暂持锁。

## 2. 派发的原子性

一次派发 `_try_dispatch` 在 `store.lock` 内完成：

1. `store.dispatchable`：按声明顺序找第一个 `PENDING` 步骤并检查依赖
   （依赖必须全部 `SUCCEEDED`），否则记录 `DEPENDENCY_NOT_MET`；
2. 在同一临界区内枚举在线单元，区分：
   - 无在线单元 → `NO_CANDIDATE_UNIT`；
   - 无能力匹配 → `CAPABILITY_MISMATCH`；
   - 能力匹配但容量都不足 → `INSUFFICIENT_CAPACITY`；
3. 选定剩余容量足够、`unit_id` 最小的单元（确定性），调用
   `unit.acquire` 原子占用；随后 `mark_dispatched` 状态流转并提交线程池。

"检查 + 占用"同锁完成，因此并发提交下不会出现超卖（容量被两个派发同时
看到并占用）。引擎另有非重入的 `_tick_guard`：任意时刻只有一次调度扫描，
保证竞争窗口内派发顺序确定、可复现。

### 2.1 派发顺序与优先级

- 每个任务在创建时分配单调递增的 `submit_seq`；调度扫描按
  **(优先级 rank, submit_seq)** 遍历任务——高优先级先派，同优先级严格
  FIFO；任务内步骤按声明顺序。该顺序只依赖创建时确定的数据，抢占重排队、
  离线重派都不会改变它，因此顺序稳定、可复现、可解释（`dispatch` 事件
  携带 `priority=`）。
- 未携带 `priority` 的提交按 `medium` 处理，与引入优先级前的行为一致。

### 2.2 抢占（让位）

当某步骤因 `INSUFFICIENT_CAPACITY` 无法派发，且其优先级**严格高于**某些
能力匹配单元上的在飞步骤时，在同一 `store.lock` 临界区内完成：

1. `_plan_preemption`：逐单元计算"空闲容量 + 可让位容量"，victim 按
   （优先级从低到高， 派发序号从晚到早） 选取，直到凑够 `capacity_cost`；
   在可行单元中选 victim 最少、`unit_id` 最小者（确定性）。同优先级
   不让位；让位后仍凑不够则不抢占（不做无谓让位）。
2. `store.preempt_step`：victim 步骤 `DISPATCHED -> PENDING`，
   `last_reject=PREEMPTED`（重新派发前粘滞保留，不被例行容量不足拒绝
   覆盖），`preemptions+1`；**不置失败码、不消耗重试额度**。
3. 立即 `release` victim 容量，随后为等待步骤 `acquire` 并派发。

整个"选 victim → 让位 → 释放 → 占用 → 派发"是原子的，因此并发提交、
取消、离线同时发生也不会超卖容量或出现账目对不上。被让位步骤飞行中
尝试的迟到结果由「状态 + 尝试代次」守卫丢弃（见 §3），不会重复释放
容量、不会计入副作用。

## 3. 执行、超时与结果收口

- 每次尝试在线程池工作线程中执行 `ExecutionUnit.run`（锁外）；
  同时启动一个 daemon 看门狗线程，`Event.wait(timeout)` 到时未完成即按
  **超时**走可恢复收口。
- 收口路径（成功 / 可恢复 / 不可恢复）都在 store 锁内执行，且带
  **尝试代次守卫**：仅当步骤仍为 `DISPATCHED` 且 `attempts == attempt+1`
  时结果才被接受。超时后的"迟到成功"、取消后的迟到结果都会被丢弃。
- 看门狗与工作线程可能同时尝试收口：代次守卫使第二个收口成为 no-op；
  容量释放统一走 `_release`，与状态收口在同一临界区，保证一次占用恰好
  释放一次（`ExecutionUnit.release` 还有超额释放断言兜底）。

## 4. 容量生命周期（无悬空占用）

容量只在 `DISPATCHED` 期间被占用，以下路径都会释放：

| 事件         | 处理                                                                 |
|--------------|----------------------------------------------------------------------|
| 成功         | `mark_succeeded` + `release`                                         |
| 可恢复失败   | 有额度：回 `PENDING` + `release`，后续重新派发再占用                  |
| 重试耗尽     | `FAILED/RETRIES_EXHAUSTED` + `release`                               |
| 不可恢复     | `FAILED/NON_RECOVERABLE` + `release`（不重试）                        |
| 高优先级抢占 | 在飞步骤回 `PENDING`（`PREEMPTED`）+ 立即 `release`；迟到结果丢弃     |
| 任务取消     | 所有未终态步骤置 `CANCELLED`，在飞占用立即 `release`；迟到结果丢弃     |
| 任务进入终态 | 级联取消同任务仍在飞步骤并 `release`（见 §4.1）                       |
| 单元离线     | `mark_offline` + 在飞步骤回 `PENDING` + 释放其占用，重派到其它单元     |

每次释放都产生 `release` 事件（含释放后剩余容量），测试用
`used == 0` 断言终态无任何悬空占用。

### 4.1 终态级联（任务终态 => 无在飞步骤）

任务因某步骤 `FAILED` 进入终态的同一临界区内，引擎把该任务其余仍在飞
的步骤级联置为 `CANCELLED` 并释放其容量；这些步骤的迟到结果会被代次
守卫丢弃，不计副作用、不改变对外视图。因此任何时刻查询都自洽：不会
出现"任务已终态却还有步骤在飞，或过一会儿又有步骤变成成功"。
（尚未派发的 `PENDING` 步骤保持 `PENDING`——任务终态后它们永远不会
再被派发，这是既有契约。）

### 4.2 重试额度与尝试代次分离

- `attempts`：派发代次（含抢占/离线后的重派），仅用于僵尸结果守卫；
- `retries_used`：只在可恢复失败（超时/异常退出）时 +1，是
  `max_retries` 的唯一计量。抢占让位、离线重排队都不消耗重试额度。

## 5. 幂等

- 提交在 store 锁内完成「检查 `task_id` 是否已存在 → 创建任务/注册行为」，
  并发重复提交只有一个线程走创建分支；其余返回同一快照、`created=false`。
- 重复提交携带的新声明/新行为被忽略，因此不会产生重复步骤或重复执行。
- 成功副作用仅在成功收口累加一次；重试链路上的失败尝试 `side_effect_count=0`。

## 6. 可观测性与可复现

- 所有关键判定产生有序 `EngineEvent(seq, kind, ...)` 并以 INFO 日志打印，
  字段包括任务/步骤/单元、任务优先级、拒绝原因（含 `PREEMPTED`）或失败码、
  尝试序号、释放前后容量；`preempt` 事件明确记录"谁让位给谁"。
- 行为脚本把"时间/故障"变成纯数据：同一组 `outcomes/delay/timeout`
  在任意机器上跑出相同的尝试次数、终态与失败原因，单测因此可复现。

## 7. 范围与非目标

- 进程内、内存态：重启数据不保留；无持久化、无消息队列、无网络 worker。
- 不接入外部服务或付费资源；不使用真实凭据。
- 线程模型仅用于模拟并发执行与竞争，生产级分布式调度不在范围内。
